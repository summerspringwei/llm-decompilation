# 项目级二进制代码恢复工作流程

英文原文：[WORKFLOW.md](WORKFLOW.md)。

修订后的八候选配置为 `coreutils_binary_candidates8.json`。下文已完成的 v2 实验仍是历史上的单候选结果。

## 适用范围与证据边界

可执行文件是主要的语义输入。Coreutils 源代码用于确定函数归属、配置测试，以及在每次恢复尝试之后导出原始代码供对照。原始应用程序的声明、函数体和 Ghidra 生成的 C 代码不作为主实验的模型输入。公共系统头文件提供外部库的 ABI 声明。依赖原始源代码框架辅助恢复的实验作为独立的对照组。

本实现面向现有的 Coreutils 9.10 构建，使用 Clang 18 和 `-O3 -fno-omit-frame-pointer` 编译选项。它不承诺恢复完整的 ELF 文件：libc、启动代码、`src/libver.a` 和 `lib/libcoreutils.a` 是允许复用的外部依赖。`df` 的应用辅助函数 `find_mount_point` 是恢复目标，不能在独立构建中直接链接其原始目标文件来替代恢复。

目标清单包含四个 `basename` 函数、五个 `uniq` 函数和十一个 `df` 函数，也包括优化后仍保留的私有头文件辅助函数。被优化完全删除或内联的函数单独记录，不为它们虚构独立函数体。

## 运行命令

使用本仓库的 Python 环境，并安装 Frida 17.4.0、pyelftools、Capstone 和配置指定的 Clang/LLVM 工具链。通过环境变量设置远程模型服务的密钥；配置文件和实验产物不得包含凭据。

```bash
export QWEN_PROJECT_API_KEY='<remote service key>'
python -m models.binary_decompilation.binary_project \
  --config models/binary_decompilation/configs/coreutils_binary_candidates8.json \
  --prepare-only
python -m models.binary_decompilation.binary_project \
  --config models/binary_decompilation/configs/coreutils_binary_candidates8.json
python -m models.binary_decompilation.project_report \
  validation/project_level_binary_v3_candidates8
```

配置中的远程端点为 `http://10.208.130.107:9001/v1`，模型为 `Qwen3.8-27B-FP8`。Qdrant 和 HermesSim 服务仍运行在本地。HermesSim 对应的集合使用 384 维向量，不能与旧的 4096 维集合混用。生成候选代码之前，预检查会验证模型服务、嵌入服务、集合和向量维度。

配置的上下文上限为每条序列 260,000 个 token，包含提示词、生成内容和推理内容。所有阶段的输出上限现均为 260,000 个 token。`remaining_context` 策略将每次请求的 `max_tokens` 设置为 `min(260000, 260000 - prompt_tokens - 64)`，避免输出预算占满上下文而没有空间容纳提示词。配置上限与实际请求额度分别保存；历史预实验使用的是较小的阶段额度。八个候选不会将单条序列的上下文上限扩大八倍。添加 `--program basename --function perform_basename --track retrieval` 可以进行指定函数的实验；应用验收仍要求完整目标清单中的函数全部通过。

## 1. 建立目标清单并分析二进制

函数归属清单使用 Clang AST 元数据和编译产生的目标文件符号。Ghidra 导出结果提供控制流图（CFG）证据和静态调用信息；只有可执行文件哈希一致时才复用这些结果。Ghidra 地址被规范化为相对于 ELF 的地址。`objdump` 提供完整的带符号反汇编。此外，还保守地考虑函数地址被引用所形成的依赖，以补充直接调用边。

每个函数都有由可执行文件哈希和函数地址组成的稳定标识。强连通分量按照先被调用者、后调用者的顺序调度。在恢复一个分量的函数体之前，先尝试恢复其所有成员的接口约定，以支持相互依赖的声明。

## 2. 建立运行时基线

首先对原始可执行文件运行上游测试和差分命令行用例。随后，在发出任何模型请求之前运行插桩基线。预加载库的构造函数会在 `main` 执行之前暂停进程，使 Frida 能够安装函数入口和返回钩子。事件记录有限范围内的参数寄存器、可读内存、全局数据快照和近似调用栈，并附带测试标识。

上游测试的跟踪结果用于补充覆盖信息和调用边。只有差分反馈用例的数值快照会进入提示词。每个函数记录八次入口观察后就停止入口采样，因此这些计数不是执行频率。`df` 中屏蔽 `/proc` 的测试只在插桩阶段排除，在原始程序和最终独立应用的测试集中仍然保留。依赖区域设置而跳过的测试仍记为跳过，不计为通过。

## 3. 推断接口约定并恢复函数体

对每个目标，通过 HermesSim/Qdrant 检索汇编相似函数。保存查询标识、集合配置、检索示例和耗时。无检索对照组省略此步骤，但保留相同的二进制分析证据。

修订配置最多保留两个相似度分数不低于 0.7 的示例。这是相关性筛选启发式，并非语义等价阈值。复用检索缓存要求查询和检索配置均匹配。

生成 JSON 格式的接口约定，其中包含函数签名、推断的项目头文件，以及可选的、有界的直接测试探针。探针类型名称遵循 [Frida NativeFunction API](https://frida.re/docs/javascript-api/#nativefunction)。执行之前验证类型、对已分配缓冲区的引用和输出边界。编译声明，并拒绝以头文件声明形式夹带的函数体。语法验证通过不代表 ABI 已被证明正确。

格式错误的探针单独报告，不再导致原本语法有效的函数签名被拒绝。如果已编译的函数体缺少执行证据，独立的探针修复阶段会生成有界探针，并重新验证同一个函数体。探针格式通过本身不能使函数被判定为恢复成功。

根据完整汇编、CFG 和调用信息、推断的被调用函数接口约定、二进制数据、公共 ABI 声明，以及运行时和检索证据生成 LLVM IR。执行 `opt -passes=verify -disable-output`，编译为位置无关代码（PIC），并在原始进程中测试候选实现。只有通过验证的 IR 才能进入 IR 到 C 的转换阶段。根据该 IR 和推断的接口约定生成 C，然后使用相同的原生函数隔离验证后端编译和测试。头文件或数据布局导致的编译失败可以触发接口约定修复和 IR 重新验证，但仍受现有请求预算约束。

签名、IR 和 C 阶段使用 `n=8`、温度 0.6、top-p 0.95，每个阶段最多十轮请求。IR 和 C 启用思考模式，签名和探针 JSON 阶段关闭思考模式：实际预实验中，启用思考的八个签名候选均耗尽 8,192 个输出 token 而未生成最终答案。探针修复最多三轮，每轮八个候选。集成阶段每轮生成一个应用连接代码候选，最多十轮。流式输出按候选索引分别记录；某个候选重复生成不会取消其他候选。所有返回的候选均保留，重复响应会复用已有验证证据并明确记录来源。优先选择通过验证的候选；若整轮失败，则选择运行时验证进展最大的候选用于下一轮编译器或运行时反馈。IR 提示词明确要求使用具名 SSA 值、正确的指针偏移类型，以及正确处理 GOT 与全局变量间接寻址。

解析器会去除内嵌思考内容，包括服务端预填充开头 `<think>` 标签的响应。启用 `ir_only_c_evidence` 时，C 阶段只接收通过验证的 IR 和接口声明，不再重复提供汇编、检索示例或运行时轨迹。

中断的请求也计入预算。连续出现相同的失败候选集合时可以提前停止。输入发生变化时创建独立修订版本，但同一阶段的所有版本共享总请求预算。保存的流式输出、提示词、响应、编译器诊断和运行时崩溃信息使失败原因可追溯；重启不会额外增加可用尝试次数。

## 4. 单独验证恢复的函数

原生函数桥接保留参数寄存器，包括可变参数调用的 ABI 状态。候选实现的全局变量被重新绑定到原始可执行文件的运行时数据。将目标函数入口重定向到恢复代码，并与原始实现比较标准输出、标准错误和退出状态。必须观察到替换函数实际进入执行。对于测试未进入的函数，使用推断的直接探针对原始函数和恢复函数进行比较，包括指定的、有界的输出缓冲区。

仅编译成功并不足够。崩溃、输出差异、未观察到替换函数入口，以及探针失败都会导致候选被拒绝。源代码框架辅助组则在原始源代码框架中编译替换实现，并单独报告回归测试是否通过；这不能证明从二进制出发的恢复成功。

辅助组的 IR 验证框架使用 `-O1` 编译，并保留声明：`-O0` 可能使 gnulib 中仅在头文件定义的内联辅助函数（例如 `mbszero`）出现未解析的符号。最初受影响的 `df` 诊断保存在 `assisted_df_before_inline_fix` 中。恢复运行时重新验证已保存的响应，不重置请求预算。

## 5. 重建并测试应用程序

只有所有必需函数的 IR 和 C 均通过验证后，集成阶段才会推断一致的声明和全局变量初始化数据。主实验的集成阶段不能重写已经通过验证的函数体。使用生成的应用代码和数据，以及经过审计的支持静态库，分别构建 IR 和 C 应用。审计生成的定义，并拒绝提供必需应用函数原始实现的静态库。

集成阶段使用差分反馈用例。随后，两个分别独立构建的最终可执行文件都必须通过配置指定的上游测试集。在原始可执行文件内部逐函数验证通过，不代表独立应用已经恢复成功。只有三个主实验应用全部通过这一验证门槛，实验目标才算完成；若在生成预算内失败，目标仍未达成。

## 实验产物与结果解读

`validation/project_level_binary_v3_candidates8` 保存解析后的配置、服务和工具链检查结果、各对照组的分析计划和基线、各函数的修订版本和尝试目录、原始源代码参考、独立构建的来源记录，以及实验与验收汇总。`REPORT.md` 和 `report.json` 根据已保存的实际结果生成，而不是依据编译成功或原始程序测试通过来推算恢复成功率。

候选产物位于 `attempt_N/choice_K` 中，`selection.json` 记录验证结果与选择。报告分别统计请求轮数、请求的候选数量（包括中断批次）和实际返回的候选数量。指定函数的实验标记为部分运行。v2 输出目录保留原始实验结果。

最初的检索预实验暴露了非法 LLVM 指针运算、字符串常量长度错误、过度重复生成，以及编译成功但运行崩溃等问题。这些尝试仍计入各自预算。由于预实验期间验证机制和提示词防护措施发生过变化，本实验属于探索性比较，并非对 RAG 收益的受控因果评估。后续受控实验应冻结代码和配置，使用新的、明确指定的实验目录，而不是删除或重置已有尝试。

## 八候选预实验

针对 `basename:perform_basename` 的预实验于 2026 年 10 月 4 日（上海时区）完成。恢复的 IR 和 C 均通过全部 11 个配置的差分测试，各观察到 10 次替换函数调用。IR 选择第八个候选，C 选择第七个候选（从零开始的位置分别为 7 和 6）。两个函数体阶段的其余七个候选均耗尽输出额度；只验证第一个候选会错过这两个通过测试的实现。

签名阶段共计四轮请求，包括两轮中断批次和一轮全部截断的思考模式批次。签名 JSON 改为非思考生成后，八个候选中有五个声明通过语法验证。IR 和 C 各使用一轮八候选请求。总计请求 48 个候选槽位，返回 32 条完整响应记录；中断请求仍计入预算。即使上下文窗口为 260,000 token，思考内容耗尽输出额度仍带来显著成本。

检索已执行，但没有相似函数达到 0.7 阈值，因此提示词未包含检索示例。该结果不能证明 RAG 收益，也不是与 v2 的受控比较。本次只选择一个函数：所选函数通过率为 1/1，占 `basename` 完整保留函数清单的 1/4。`main`、`oputs_` 和 `usage` 在此次预实验中未尝试，尚未恢复独立应用。详见[保存的报告](../../validation/project_level_binary_v3_candidates8/REPORT.md)，以及 `retrieval/basename/functions/perform_basename` 下的 `signature/latest.json`、`ir/latest.json` 和 `c/latest.json`，其中记录候选文件路径及验证证据。

## 已知限制

- 默认分析器要求带符号的 Linux x86-64 ELF，以及用于确定函数归属的源代码和构建元数据；尚未实现去符号二进制的函数发现。
- 近似调用栈和保守的函数地址引用边无法解析所有间接调用、回调和经过优化的尾调用。
- 尚未实现大型函数的 CFG 分区恢复；上下文过大时明确记录为失败，而不是视为函数已经恢复。
- 输出限制，以及基于启发式的重复生成和停滞检测，可能在候选代码完整生成之前终止生成；这些停止属于失败，不是语义正确性的判定。
- 推断的数据布局和函数签名在经过行为验证之前都只是待验证的假设。
- 测试覆盖的是已经观察到的行为，而不是所有输入或涉及未定义行为的情况。
- 复用支持库意味着重建应用程序，而不是重新生成整个 ELF 或恢复库函数实现。
- 辅助组验证通过时，被替换函数可能并未实际执行；不能将此结果表述为具有独立执行证据的函数等价性验证。
- 原生验证会执行生成的机器代码，并不提供安全沙箱。对于不可信的输入和候选代码，应使用隔离的执行环境。
